# Minishell 設計判断と技術選択

## 1. 概要

このドキュメントは、Minishellプロジェクトにおける主要な設計判断と技術選択について説明します。各検討ポイントについて、利用可能な選択肢、それぞれの利点・欠点、最終的な選択とその理由を記載します。

## 2. アーキテクチャ選択

### 2.1 全体アーキテクチャ

#### 検討した選択肢

| アプローチ | 利点 | 欠点 |
|-----------|------|------|
| **モノリシック** | - シンプルな構造<br>- 関数間の直接呼び出し<br>- デバッグが容易 | - 拡張性が低い<br>- テストが困難<br>- コードの再利用性が低い |
| **レイヤード** | - 明確な責任分離<br>- テスト容易性<br>- 段階的な開発が可能 | - レイヤー間の調整が必要<br>- やや複雑な構造 |
| **パイプライン** | - データフローが明確<br>- 各段階が独立 | - エラー処理が複雑<br>- 状態管理が困難 |

#### 選択：レイヤードアーキテクチャ

**理由：**
- レキサー → パーサー → エグゼキューターの明確な分離
- 各層を独立してテスト可能
- 42ノームの制約（ファイルあたり5関数）と相性が良い
- bashの内部構造を参考にした実装

### 2.2 データフロー設計

```
入力 → [Lexer] → トークン列 → [Parser] → AST → [Executor] → 実行結果
         ↓                        ↓                    ↓
      字句解析                構文解析            コマンド実行
```

## 3. レキサー（字句解析器）設計

### 3.1 実装方式

#### 検討した選択肢

| 方式 | 利点 | 欠点 |
|------|------|------|
| **手書きレキサー** | - 完全な制御<br>- カスタマイズ容易<br>- 学習価値が高い | - 実装に時間がかかる<br>- バグが入りやすい |
| **正規表現ベース** | - 実装が簡潔<br>- パターンマッチが明確 | - Cでの正規表現は複雑<br>- パフォーマンス問題 |
| **状態機械** | - 効率的<br>- 理論的に堅固 | - 実装が複雑<br>- デバッグが困難 |

#### 選択：手書きレキサー（文字単位スキャン）

**理由：**
- シェルの字句規則は比較的単純
- クォート処理や変数展開の細かい制御が必要
- 42の学習目的に合致
- デバッグとメンテナンスが容易

### 3.2 トークン管理

#### 検討した選択肢

| 方式 | 利点 | 欠点 |
|------|------|------|
| **配列** | - ランダムアクセス可能<br>- メモリ効率的 | - サイズ変更が困難<br>- 挿入・削除が非効率 |
| **連結リスト** | - 動的なサイズ<br>- 挿入・削除が容易 | - ランダムアクセス不可<br>- メモリオーバーヘッド |

#### 選択：連結リスト

**理由：**
- トークン数が事前に不明
- 順次アクセスで十分
- メモリ管理が明確

## 4. パーサー（構文解析器）設計

### 4.1 パース手法

#### 検討した選択肢

| 手法 | 利点 | 欠点 |
|------|------|------|
| **再帰下降構文解析** | - 実装が直感的<br>- デバッグ容易<br>- エラー処理が簡単 | - 左再帰に対応不可<br>- スタック使用量 |
| **演算子順位法** | - 効率的<br>- 少ないメモリ使用 | - 複雑な文法に不適<br>- 実装が難しい |
| **LRパーサー** | - 強力な解析能力<br>- 理論的基盤 | - 実装が複雑<br>- テーブル生成が必要 |

#### 選択：再帰下降構文解析

**理由：**
- シェルの文法は左再帰を含まない
- 実装と理解が容易
- エラーメッセージの生成が簡単
- 42ノームの関数制限と相性が良い

### 4.2 AST（抽象構文木）

#### 検討した選択肢

| 方式 | 利点 | 欠点 |
|------|------|------|
| **AST構築** | - 構造が明確<br>- 複数回の走査可能<br>- 最適化可能 | - メモリ使用量<br>- 構築のオーバーヘッド |
| **直接実行** | - メモリ効率的<br>- 高速実行 | - 複雑な制御フロー<br>- デバッグ困難 |

#### 選択：AST構築

**理由：**
- パイプラインやリダイレクションの処理が明確
- デバッグとテストが容易
- 将来の拡張（&&、||など）に対応しやすい

## 5. エグゼキューター（実行エンジン）設計

### 5.1 プロセス管理

#### 検討した選択肢

| 方式 | 利点 | 欠点 |
|------|------|------|
| **単純fork** | - 実装が簡単<br>- 理解しやすい | - ビルトインで非効率<br>- リソース消費 |
| **条件付きfork** | - ビルトイン最適化<br>- 効率的 | - 複雑な条件分岐<br>- エッジケース対応 |
| **vfork使用** | - 高速<br>- メモリ効率的 | - 制限が多い<br>- 移植性の問題 |

#### 選択：条件付きfork（ビルトイン最適化あり）

**理由：**
- 単独ビルトインコマンドはforkしない
- パイプライン内では全てfork
- パフォーマンスとシンプルさのバランス

### 5.2 パイプライン実装

#### 検討した選択肢

| 方式 | 利点 | 欠点 |
|------|------|------|
| **逐次実行** | - シンプル<br>- デバッグ容易 | - 効率が悪い<br>- 実際のシェルと異なる |
| **並列fork** | - 効率的<br>- 実際のシェルに近い | - 同期が複雑<br>- エラー処理が困難 |

#### 選択：並列fork

**理由：**
- bashと同様の動作
- パフォーマンスの向上
- リアルなシェル体験の提供

## 6. メモリ管理

### 6.1 メモリ割り当て戦略

#### 検討した選択肢

| 戦略 | 利点 | 欠点 |
|------|------|------|
| **都度malloc/free** | - メモリ効率的<br>- 明確な所有権 | - 管理が複雑<br>- リーク発生リスク |
| **メモリプール** | - 高速割り当て<br>- 一括解放可能 | - 実装が複雑<br>- メモリの無駄 |
| **ガベージコレクション** | - 自動管理<br>- リーク防止 | - Cでは困難<br>- オーバーヘッド |

#### 選択：都度malloc/free

**理由：**
- Cの標準的な方法
- valgrindでのデバッグが容易
- 42の評価基準に合致
- 明確なメモリ所有権

### 6.2 エラー時のクリーンアップ

#### 実装方針
```c
// 各レベルでのクリーンアップ関数
- cleanup_tokens()    // トークンリスト解放
- cleanup_ast()       // AST解放
- cleanup_shell()     // シェル全体のクリーンアップ
```

## 7. シグナル処理

### 7.1 シグナルハンドリング方式

#### 検討した選択肢

| 方式 | 利点 | 欠点 |
|------|------|------|
| **signal()** | - シンプル<br>- 移植性が高い | - 非推奨<br>- 制限が多い |
| **sigaction()** | - 詳細な制御<br>- POSIX標準 | - やや複雑<br>- 設定項目が多い |

#### 選択：sigaction()

**理由：**
- より細かい制御が可能
- SA_RESTARTフラグなどの利用
- 現代的なシグナル処理

### 7.2 グローバル変数の使用

#### 制約と対応
- 42の制約：グローバル変数は1つのみ
- 選択：`volatile sig_atomic_t g_signal_received`
- 理由：シグナルハンドラーとメインループ間の通信に必要

## 8. 環境変数管理

### 8.1 データ構造

#### 検討した選択肢

| 構造 | 利点 | 欠点 |
|------|------|------|
| **配列（char**）** | - 既存APIとの互換性<br>- シンプル | - 変更が非効率<br>- 検索がO(n) |
| **連結リスト** | - 動的な追加・削除<br>- メモリ効率的 | - 検索がO(n)<br>- 配列への変換必要 |
| **ハッシュテーブル** | - 高速検索O(1)<br>- 効率的 | - 実装が複雑<br>- メモリオーバーヘッド |

#### 選択：連結リスト + 配列のハイブリッド

**理由：**
- 内部管理は連結リスト（`t_env`）
- execve用に配列に変換
- 追加・削除の柔軟性と互換性の両立

## 9. エラーハンドリング

### 9.1 エラー報告方式

#### 検討した選択肢

| 方式 | 利点 | 欠点 |
|------|------|------|
| **戻り値** | - シンプル<br>- 明確 | - エラー詳細が不明<br>- エラーコードの管理 |
| **errno** | - 標準的<br>- 詳細情報 | - グローバル状態<br>- スレッドセーフでない |
| **専用構造体** | - 詳細な情報<br>- 拡張性 | - 複雑<br>- オーバーヘッド |

#### 選択：戻り値 + stderr出力

**理由：**
- bashと同様のエラー表示
- シンプルで理解しやすい
- 42の要件に適合

### 9.2 エラーコード

```c
#define ERROR_GENERAL       1
#define ERROR_BUILTIN       2  
#define ERROR_EXEC          126
#define ERROR_CMD_NOT_FOUND 127
#define ERROR_SIGNAL_BASE   128
```

## 10. ヒアドキュメント実装

### 10.1 処理タイミング

#### 検討した選択肢

| タイミング | 利点 | 欠点 |
|---------|------|------|
| **パース時** | - 早期処理<br>- シンプルなAST | - パーサーが複雑化<br>- Ctrl+C処理が困難 |
| **実行時** | - 遅延評価<br>- 柔軟な処理 | - 実行が複雑<br>- パイプ管理 |

#### 選択：実行時処理

**理由：**
- Ctrl+Cによる中断が可能
- bashと同様の動作
- パーサーの簡潔性維持

### 10.2 入力処理

#### 実装方式
- インタラクティブ：fork + readline
- 非インタラクティブ：get_next_line
- 理由：適切なシグナル処理とプロンプト表示

## 11. 42ノーム対応

### 11.1 関数分割戦略

#### 制約
- 1関数25行以内
- 1ファイル5関数以内
- 最大4パラメータ

#### 対応方針
1. **機能単位での分割**：論理的なまとまりを保持
2. **ヘルパー関数の活用**：複雑な処理を小関数に分割
3. **utilsファイルの活用**：共通処理を別ファイルに

### 11.2 ファイル構成

```
src/
├── builtin/      # 各ビルトイン + utils
├── env/          # 環境変数管理
├── error/        # エラー処理
├── executor/     # 実行エンジン（細分化）
├── lexer/        # レキサー（8ファイル）
├── parser/       # パーサー（6ファイル）
├── signal/       # シグナル処理
└── utils/        # 共通ユーティリティ
```

## 12. テスト戦略

### 12.1 テストアプローチ

#### 選択：段階的テスト
1. **ユニットテスト**：各コンポーネント個別
2. **統合テスト**：コンポーネント間連携
3. **E2Eテスト**：実際のシェル動作

#### 理由
- バグの早期発見
- リグレッション防止
- 仕様準拠の確認

## 13. 今後の拡張性

### 13.1 ボーナス機能への対応

#### 準備済みの拡張ポイント
- **論理演算子（&&、||）**：ASTノードタイプの追加で対応可
- **括弧**：パーサーの拡張で対応可
- **ワイルドカード**：既に基本実装済み

### 13.2 設計の柔軟性

- モジュラー設計により機能追加が容易
- 各層の独立性により局所的な変更で対応可能
- テストの充実により安全な拡張が可能

## 14. 結論

### 14.1 主要な設計判断

1. **レイヤードアーキテクチャ**：明確な責任分離
2. **手書きレキサー・パーサー**：学習価値と制御性
3. **AST構築**：構造の明確さとデバッグ容易性
4. **条件付きfork**：パフォーマンスの最適化
5. **連結リスト多用**：動的データ構造への対応

### 14.2 トレードオフ

- **複雑性 vs 保守性**：やや複雑だが保守しやすい設計を選択
- **パフォーマンス vs シンプルさ**：基本的にシンプルさを優先、必要な箇所のみ最適化
- **メモリ vs 速度**：適度なメモリ使用を許容し、コードの明確さを優先

### 14.3 成功要因

1. bashの動作を詳細に研究
2. 段階的な実装とテスト
3. 42ノームの制約を設計に組み込み
4. エラー処理の一貫性
5. メモリ管理の徹底

この設計により、bashライクな動作をする堅牢なシェルの実装を実現しました。
